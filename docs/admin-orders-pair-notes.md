## 0. 오늘의 한 줄

> 주문 목록 화면을 만들기 전에, **DB가 우리가 믿는 모습과 같은지 먼저 의심한 것**이 오늘 제일 잘한 일이야. 기능은 누구나 만든다. 시니어는 "내 전제가 맞나?"를 먼저 친다.

---

## 1. 코드 짜기 전에 — "전제를 의심하라"

화면을 만들려고 `types/index.ts`를 봤더니 `Order.total_price`, `Customer.memo`가 있었어. 그런데 `supabase/schema.sql`엔 그 컬럼이 **없었어.**

여기서 주니어와 시니어가 갈려.

- **주니어**: 타입에 있으니 있겠지 → 바로 화면 코드 작성 → 운 좋으면 동작, 운 나쁘면 운영 중 터짐.
- **시니어**: "둘 중 하나는 거짓말이다." 코드를 멈추고 **사실을 확인**한다.

우리가 한 건 이거야 — 라이브 DB에 **읽기 전용으로** 로그인해서 컬럼 존재를 직접 조회:

```
login OK
orders.total_price: EXISTS
customers.memo: EXISTS
orders rows: 9
```

결론: **schema.sql이 낡았고**, 실제 DB·코드는 정상. 만약 반대였다면(코드가 거짓) 소비자 주문이 깨져 있었을 거고, 그걸 모른 채 관리자 화면을 얹었으면 디버깅 지옥에 빠졌겠지.

### 가져갈 교훈
- **"타입에 있다 ≠ DB에 있다."** 타입은 사람이 쓴 약속이고, 약속은 어긋난다.
- 검증할 때 **데이터를 더럽히지 마라.** 우리는 `SELECT`만 했고, 테스트로 바꾼 주문 상태는 끝나고 원복했다. 남의 운영 DB는 "내가 들어왔던 흔적이 없게" 나오는 게 기본 예의야.
- 의심이 들면 **5분 검증이 5시간 디버깅을 막는다.** 거의 항상 남는 장사.

## 2. 드리프트를 "고치는 법"의 절제

컬럼 4개가 누락된 걸 찾고 나서, 욕심이 생겨. "이왕 보는 거 트리거도, seed도 다 정리할까?"

여기서 **선을 그었어:**

| 했다 | 안 했다 | 왜 |
|------|--------|-----|
| 검증된 컬럼 4개 추가 | 트리거 DDL 추측해서 작성 | 트리거는 PostgREST로 실물을 못 봐. **못 보는 걸 지어내면 그게 새 거짓말이다.** |
| `-- DRIFT NOTE`로 트리거 존재를 명시 | seed.sql 값 보정 | seed는 이미 동작함. 안 깨진 걸 건드리는 건 리스크만 추가. |

이게 **외과적 변경(surgical change)**의 핵심이야. "정확히 아는 것만 고치고, 모르는 건 정직하게 깃발 꽂아둔다." 모르는 걸 그럴듯하게 채우는 게 제일 위험한 습관이야 — 나중에 그 추측을 사실로 믿게 되거든.

> 💡 권위 있는 스키마가 필요하면 추측 대신 `supabase db dump --schema public`. 도구가 사실을 뱉게 해라.

## 3. 아키텍처 — "방향 있는 의존성"을 지키는 작은 트릭

FSD(entities / features / shared)에는 철칙이 하나 있어: **의존성은 한 방향으로만 흐른다.**

```
app  →  features  →  entities  →  shared
(위가 아래를 import 한다. 절대 역방향 금지)
```

문제 상황: 주문 카드(`OrderCard`, **entities** = 표시)는 상태 변경 버튼(`OrderStatusControl`, **features** = 행동)을 품어야 자연스러워 보여. 그런데 entities가 features를 import하면? **화살표가 거꾸로 꽂혀서 규칙이 깨져.**

우리가 쓴 해법 — **children 슬롯:**

```tsx
// entities/order/ui/OrderCard.tsx  (features를 1도 모름)
export function OrderCard({ order, children }) {
  return <div>...<div className="action">{children}</div></div>;
}

// app/admin/dashboard/orders/page.tsx  (조립은 위 레이어가)
<OrderCard order={o}>
  <OrderStatusControl orderId={o.id} status={o.status} />
</OrderCard>
```

`OrderCard`는 "여기 액션 자리 하나 비워둘게"라고만 말하고, **무엇이 들어올지는 모른다.** 조립은 가장 위 레이어(page)가 한다.

### 왜 이게 중요한가
- 이건 React의 일반 원칙이기도 해 — **"제어의 역전(Inversion of Control)".** 컴포넌트가 자식을 직접 고르는 대신, 부모가 주입한다. 재사용성과 테스트성이 같이 올라가.
- 당장은 "그냥 import하면 되잖아?" 싶지만, 이 한 번의 타협이 6개월 뒤 **순환 의존성과 "이거 왜 못 빼?"의 시작점**이야. 경계는 작을 때 지켜야 공짜다.

## 4. 상태 변경 — 낙관적 UI를 일부러 **안** 썼다

상태 바꾸는 버튼, 두 가지 길이 있어:

1. **낙관적(optimistic)**: 클릭 즉시 화면을 바꾸고, 서버는 뒤에서 따라옴. 빠르게 *느껴짐*.
2. **서버 신뢰(server-authoritative)**: 서버액션 실행 → `revalidatePath` → 서버가 다시 그림.

우리는 **2번**을 골랐어. 왜?

- 이건 **돈이 오가는 운영 화면**이야. "입금 확인"을 눌렀는데 사실 DB 반영이 실패했고 화면만 바뀌었다면? 아버지는 입금 안 된 주문을 발송해버려. **낙관적 UI의 거짓말이 여기선 실제 손실이야.**
- 주문량도 적어(9건). 낙관적 UI가 가리려는 "지연"이 체감되지도 않는 규모야. **없는 문제를 풀지 마라.**

> 규칙: **낙관적 UI는 "틀려도 손해 없는 곳"에 써라.** 좋아요·읽음표시엔 좋고, 결제·재고·배송 상태엔 신중해야 해. (참고로 소비자 피드의 낙관적 UI는 옳은 선택이었어 — 거기선 틀려도 손해가 없거든.)

`revalidatePath` 한 줄이 배지·버튼·헤더 카운트(`입금대기 3→2`)를 한 번에 다시 그려주는 것도 봤지? 서버를 단일 진실 공급원(source of truth)으로 두면 **여러 군데를 수동으로 맞출 필요가 없어진다.** 이게 "상태를 한 곳에서만 관리"의 실전 이득이야.

## 5. 타입이 막을 때 — 도망치는 법도 기술이다

두 군데서 타입 에러가 났고, 대응이 **서로 달랐어.** 이 차이가 중요해.

### (a) `.returns<>()` — 도구의 한계를 인정하고 우회
`Database` 타입의 `Relationships: []`가 비어서 supabase-js가 조인 타입을 추론 못 했어. 런타임 조인은 **REST로 이미 검증**했고. 그래서:

```ts
.returns<OrderJoinRow[]>()   // "실제 응답은 이 모양이야"라고 내가 보증
```

이건 정당한 탈출구야 — **내가 사실을 알고**(검증함), 도구만 못 따라오는 상황이니까. 근본 해결(타입에 Relationships 채우기)은 주석으로 남겨 다음으로 미뤘어.

### (b) `cancelled` 상태 — 타입이 진짜 버그를 잡아줌
`entities`의 `OrderStatus`엔 `cancelled`가 있는데 **DB의 CHECK 제약엔 없어.** 만약 cancel 버튼을 만들었으면 DB가 런타임에 거부했을 거야. 타입 에러가 이걸 **컴파일 타임에** 미리 비명 질러준 거지.

→ 그래서 UI 흐름에서 cancel을 빼고, 서버액션에도 방어 가드를 넣었어:
```ts
if (!ORDER_FLOW.includes(status)) throw ...  // DB와 같은 규칙을 코드에도
```

### 가져갈 교훈
**타입 에러를 만났을 때 매번 자문해라: "이게 도구의 한계냐, 아니면 진짜 버그를 잡아준 거냐?"**
- 한계면 → 검증 후 명시적으로 우회(`as`, `.returns`)하고 *왜 안전한지 주석*.
- 진짜 버그면 → `as`로 입 막지 말고 **설계를 고쳐라.** `as any`로 빨간 줄만 지우는 건 타입시스템에게 "닥쳐"라고 하는 거고, 그 버그는 사라진 게 아니라 **숨은 거야.**

## 6. RLS — "이미 되어 있던 것"을 알아본 것도 일이다

주문 조회는 관리자만 돼야 해. 새 권한 코드를 짜려다 `schema.sql`을 보니:

```sql
create policy "orders_select" on orders for select using (auth.role() = 'authenticated');
```

**이미 깔려 있었어.** STEP 3의 인증 게이트(`proxy.ts`)로 로그인하면 세션 쿠키가 서버 클라이언트에 실려가고, RLS가 알아서 통과시켜. **추가로 짤 게 없었다.**

교훈: **새 코드를 짜기 전에 "이미 있는 거 아냐?"를 먼저 본다.** 가장 좋은 코드는 안 짜도 되는 코드야. 신입은 기능을 추가해서 점수를 따려 하고, 시니어는 **이미 있는 메커니즘에 올라타서** 표면적을 줄인다.

## 7. 한눈에 — 오늘 쓴 시니어 휴리스틱

1. **전제를 의심하고, 코드 대신 사실을 먼저 쳐라.** (드리프트 검증)
2. **검증은 흔적 없이.** 읽기 전용, 바꿨으면 원복.
3. **아는 것만 고치고, 모르는 건 깃발을 꽂아라.** (트리거 DRIFT NOTE)
4. **경계는 쌀 때 공짜다.** (children 슬롯으로 의존성 방향 유지)
5. **낙관적 UI는 틀려도 손해 없는 곳에만.** (결제/배송은 서버 신뢰)
6. **타입 에러: 한계인가 버그인가를 구분하라.** `as any`는 침묵이지 해결이 아니다.
7. **새로 짜기 전에 이미 있는 걸 찾아라.** 안 짠 코드가 제일 안전하다.

## 8. 다음에 같이 볼 것 (상품 등록/수정)

미리 던지는 떡밥 — 다음 화면에서 마주칠 판단들:
- **이미지 업로드**: Supabase Storage 버킷 정책은 이미 있어(`images_insert` = authenticated). 또 "이미 있는 것"부터 확인하고 시작.
- **stock 트리거와의 상호작용**: 주문 시 재고 자동 감소 트리거가 라이브에 있어(§2 DRIFT NOTE). 상품 수정에서 stock을 직접 건드릴 때 트리거와 충돌하지 않는지 **먼저 동작을 관찰**하고 설계하자. (또 전제 의심!)
- **낙관적 UI 재등장 가능**: 상품 목록 토글(노출/숨김) 같은 건 틀려도 손해가 작아 — 거긴 낙관적이 맞을 수 있어. §4의 기준으로 매번 새로 판단.
