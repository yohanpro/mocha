# 관리자 피드 등록/관리 — 페어 세션 노트

>
> "무엇을"은 [manage-feed-technical-spec.md](manage-feed-technical-spec.md)에. 여기선 **왜 그렇게 했고, 다음에 뭘 조심할지**.

---

## 0. 오늘의 한 줄

> 바로 앞 노트가 **"다음에 같이 볼 것"으로 이 기능을 예고**해뒀어([products §7](admin-products-pair-notes.md)). 떡밥을 회수하면서 두 개를 정리했다 — **하나는 회수했고(youtube 유틸 재사용), 하나는 의식적으로 미뤘다(업로드).**

---

## 1. 왜 "등록/수정 통합"을 안 하고 "등록만" 했나

상품에선 `saveProduct` 하나로 등록·수정을 합쳤어([products §3](admin-products-pair-notes.md)). 바로 다음 기능인데 여기선 **정반대로 수정 자체를 안 만들었다.** 일관성 없어 보이지? 아니야 — **도메인이 다르면 정답도 다르다.**

- **상품**은 살아있는 운영 데이터야. 가격·재고·상태가 **계속 바뀐다.** 수정은 필수 기능.
- **피드 글**은 소셜 게시물이야. 한 번 올리면 **거의 안 고친다.** 인스타 게시물을 편집하는 일이 얼마나 되나? 오타 나면 지우고 다시 올리지.

그래서 판단: **수정의 실제 수요가 삭제+재등록 비용보다 작다.** 안 만들었어.

### 가져갈 교훈
- **"상품에서 했으니 피드도 똑같이"는 게으른 대칭이야.** 패턴 재사용은 좋지만, 재사용 전에 "이 도메인에서도 그 가정이 참인가?"를 물어. 여기선 "데이터가 자주 바뀐다"는 가정이 깨졌어.
- **안 만든 것도 결정이다.** 수정 폼·수정 라우트·`saveProduct`식 `id` 분기 — 다 안 짰어. YAGNI: 수요가 증명되면 그때. 지금은 삭제로 충분.

## 2. 이미 있는 걸 찾아라 — youtube 유틸 재사용 (떡밥 회수 ①)

`savePost`의 유튜브 URL 검증:

```ts
if (!extractYoutubeId(youtubeUrl)) return { error: "유튜브 링크 형식이..." };
```

`extractYoutubeId`는 **소비자 피드가 이미 쓰던** `shared/utils/youtube.ts`의 함수야. 정규식으로 `watch?v=`, `youtu.be/`, `shorts/` 세 형식을 파싱해.

여기서 신입이 하기 쉬운 실수: **"URL 검증? 정규식 새로 짜야지"** 하고 `savePost` 안에 또 하나 만드는 것. 그럼 소비자 피드가 렌더하는 파싱 규칙과 **등록 시 검증하는 규칙이 갈라져** — 등록은 통과했는데 렌더가 안 되는 게시물이 생겨.

> 원칙: **검증과 사용은 같은 함수를 봐야 한다.** "저장할 때 통과한 규칙"과 "보여줄 때 파싱하는 규칙"이 물리적으로 같은 코드면, 둘이 어긋날 수가 없어. 새로 짜기 전에 `shared/`부터 뒤져라.

## 3. 조회는 왜 또 둘로 나눴나 — `getPosts` vs `getAllPosts`

```
getPosts({ cursor, limit })   // 소비자: 무한스크롤 페이지네이션
getAllPosts()                 // 관리자: 전체 최신순
```

[products §3](admin-products-pair-notes.md)의 "불리언 플래그 매개변수는 함수 둘의 신호" 그대로야. 여기선 플래그도 아니고 **관심사 자체가 달라** — 소비자는 페이지네이션이 핵심이고, 관리자는 "다 보여줘"가 핵심. `getPosts`에 `limit: 9999`를 넘겨 우회할 수도 있었지만, 그건 **호출부의 의도를 숨기는 것.** 이름이 의도를 말하게 뒀어.

기존 `getPosts`는 **한 글자도 안 건드렸다** — 소비자 피드가 의존하는 코드라, 외과적 변경 원칙(건드릴 것만 건드려).

---

## 4. 삭제엔 낙관적 UI를 왜 안 썼나

주문 상태 변경도, 이 삭제도 **서버 확정 후 재렌더**야(낙관적 UI 없음). [design-notes §7](design-notes.md)의 "낙관적 UI는 틀려도 손해 없는 곳에만" 적용.

- 소비자 피드 스크롤 = 틀려도 손해 없음 → 낙관적 OK
- **삭제 = 되돌릴 수 없음** → 서버가 "진짜 지웠다"를 확인하기 전에 UI에서 지우면, 실패 시 "사라진 줄 알았는데 살아있는" 유령 상태가 돼. 운영자가 다시 지우려다 혼란.

`<form action={deletePost}>` + hidden `id`의 서버 액션 바인딩을 쓴 것도 이 때문 — 클라이언트 상태 없이 서버가 목록을 다시 그린다. **가장 단순한 게 가장 안전한 자리.**

---

## 5. 업로드는 이번에도 안 만들었다 (떡밥 회수 ②, 의식적 보류)

[products §7](admin-products-pair-notes.md)에서 "피드는 사진이 핵심이라 URL vs 업로드를 다시 마주친다"고 적었지. 마주쳤고 — **또 URL로 갔다.**

왜 또 미뤘나:
- 버킷 생성은 **네 대시보드 작업**이 필요하고(외부 의존), 업로드 UX(폰에서 촬영→업로드)는 별도 설계야. [products §2](admin-products-pair-notes.md)의 "혼자 되돌릴 수 있나 + 네 행동이 필요한가" 계산에서 **둘 다 걸려.**
- 그리고 지금 목표는 **7/31 완주**([design-notes §10](design-notes.md)). URL 방식으로도 등록·판매·검증이 다 돌아. 업로드는 MVP 완주에 필수가 아니야.

> 이건 게으름이 아니라 **범위 규율**이야. "이왕 하는 김에 업로드도"가 데드라인을 죽여. 지금 필요한 최소를 짜고, 업로드는 #3으로 깃발만 꽂아둔다. **회수할 준비가 된 떡밥과, 지금 회수할 떡밥은 다르다.**

단, 그때 만들면 업로드 로직은 **상품·피드 공용**으로 빼라(중복 금지). 여전히 유효한 계획.

---

## 6. 검증은 실제로, 흔적 없이 (또)

[products §5](admin-products-pair-notes.md) 그대로 실행했어:
1. `[검증용]` 접두사 사진 게시글 등록 → 관리자 목록 상단 + **소비자 `/feed` "오늘" 최상단** 반영 확인
2. 이미지 도메인은 `unsplash`로 골라 소비자 피드의 `next/image`까지 실제 렌더되는지 확인 (관리자 목록은 `<img>`라 아무 URL이나 뜨지만, 소비자는 `remotePatterns` 게이트를 통과해야 함 — 여기서 안 골랐으면 "관리자엔 뜨는데 소비자엔 깨지는" 걸 놓쳤을 것)
3. 끝나고 그 글을 **삭제**해 원상복구

교훈 하나 추가: **"어디서 렌더되는지"에 따라 테스트 데이터도 골라야 한다.** 대충 아무 이미지 URL로 테스트했으면 소비자 피드에서 깨지는 걸 못 봤어. 검증은 **가장 까다로운 렌더 경로**를 기준으로.

## 7. 한눈에 — 오늘 추가된 휴리스틱

1. **패턴 재사용 전에 도메인 가정을 검사하라.** "상품에서 했으니 피드도"는 게으른 대칭. 수정 수요가 없으면 수정을 안 만드는 게 정답.
2. **검증 규칙과 사용 규칙은 같은 함수를 보게 하라.** 저장 시 통과한 규칙 = 렌더 시 파싱 규칙. 새로 짜기 전 `shared/` 검색.
3. **낙관적 UI는 가역적인 곳에만.** 삭제처럼 되돌릴 수 없는 건 서버 확정 후 재렌더.
4. **범위 규율 = 떡밥을 골라 회수.** "이왕 하는 김에"가 데드라인을 죽인다. 지금 필요한 최소 + 나머진 깃발.
5. **테스트 데이터는 가장 까다로운 렌더 경로 기준으로 고른다.** 아무 값이나 넣으면 경로별 차이를 놓친다.
