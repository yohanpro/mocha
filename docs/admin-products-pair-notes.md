## 0. 오늘의 한 줄

> 똑같은 실수를 **세 번째** 잡았다. "전제를 의심하라"가 1회성 영웅담이 아니라 **루틴**이 되면, 그게 진짜 실력이야.

---

## 1. §1 교훈, 세 번째 — 이번엔 "기능 자체"를 살렸다

[주문 목록 노트 §1](admin-orders-pair-notes.md)에서 스키마 드리프트를 잡았지. 이번에도 코드 짜기 전에 전제를 쳤더니 **둘이 나왔어:**

1. `products.description` — 타입엔 있고 schema.sql엔 없음 (또 드리프트)
2. **`images` Storage 버킷이 라이브에 존재하지 않음** (`Bucket not found`)

2번이 핵심이야. 만약 의심 안 하고 **"이미지 업로드 폼"부터 만들었으면?**
- 폼 만들고 → 업로드 코드 짜고 → 테스트 → `Bucket not found` 에러 → "어? 정책도 schema.sql에 있는데?" → 한참 헤매다 → "버킷이 실제로 안 만들어졌네"를 **맨 마지막에** 발견.

전제를 먼저 쳐서 **그 한나절을 통째로 건너뛰고**, 시작부터 "URL 방식"이라는 옳은 길로 들어섰어.

### 가져갈 교훈
- **"선언했다 ≠ 존재한다."** schema.sql에 `insert into storage.buckets`가 있다고 버킷이 라이브에 있는 게 아니야. SQL 파일은 의도지 실재가 아니다.
- 검증의 ROI는 **기능이 복잡할수록 커진다.** 단순 조회면 몰라도, 외부 인프라(Storage, 큐, 결제)가 끼면 "있는 줄 알았는데 없는 것"이 제일 비싼 버그야. **만들기 전에 핑 한 번.**

## 2. 언제 직접 결정하고, 언제 물어보나

우리 작업 원칙은 "결정 가능한 건 직접 결정"이야. 그런데 이미지 전략(URL vs 업로드)은 **내가 안 정하고 너한테 물었어.** 왜 이건 예외였나?

| 직접 결정한 것 | 물어본 것 |
|---|---|
| 드리프트를 어떻게 고칠지 | 이미지를 URL로 받을지 업로드할지 |
| 검증 컬럼만 schema에 추가 | |
| create/edit 액션 통합 | |

차이는 **"되돌리기 비용 + 외부 의존"**이야.
- 코드 구조 결정 → 틀려도 내가 리팩토링하면 끝. **싸고 가역적** → 직접 결정.
- 이미지 전략 → 업로드를 고르면 **너의 대시보드 작업(버킷 생성)**이 필요하고, 제품의 방향(폰 업로드 UX)을 가른다. **비싸고 외부 의존** → 물어봐야 함.

> 휴리스틱: **"내가 혼자 되돌릴 수 있나? 너의 행동이 필요한가?"** 둘 다 OK면 그냥 진행하고 근거만 말해. 하나라도 걸리면 멈추고 물어봐. 시니어가 일을 막 진행하는 것 같아도, 사실 이 선을 매번 계산하고 있어.

## 3. 함수 하나가 두 일을 — 좋은 통합 vs 나쁜 통합

`saveProduct` 하나가 등록과 수정을 다 해. `formData`에 `id`가 있으면 update, 없으면 insert.

```ts
const { error } = id
  ? await supabase.from("products").update(row).eq("id", id)
  : await supabase.from("products").insert(row);
```

"함수 하나가 두 가지 일을 하면 나쁜 거 아냐?"라고 배웠을 텐데 — **맥락에 따라 달라.**
- **좋은 통합:** 등록/수정은 입력 검증·필드 매핑·리다이렉트가 **95% 동일**해. 분기점은 마지막 한 줄(insert vs update)뿐. 둘로 쪼개면 같은 검증 로직을 두 곳에 복붙하게 되고, 한쪽만 고치는 버그가 생겨. → **공통이 압도적이면 합치고 차이만 분기.**
- **나쁜 통합:** 만약 등록과 수정의 검증 규칙·권한·부작용이 전혀 다른데 억지로 `if`로 욱여넣으면? 그건 "두 함수를 한 몸에 가둔 것"이고 읽기 지옥이야.

판단 기준: **"분기 로직이 공통 로직보다 작은가?"** 작으면 합쳐. 분기가 본문을 잡아먹기 시작하면 쪼개.

반대 사례도 봐 — 조회는 **일부러 둘로 나눴어:**
```
getProducts()      // 소비자: hidden 제외
getAllProducts()   // 관리자: 전체
```
"파라미터 하나로 `getProducts(includeHidden)` 하면 되잖아?" 싶지? 안 그런 이유: **호출하는 쪽의 의도가 이름에 박히는 게** `boolean` 인자보다 안전해. 소비자 페이지에서 실수로 `getProducts(true)`를 호출해 숨김 상품을 노출하는 사고를, 함수가 아예 분리돼 있으면 칠 수가 없어. **불리언 플래그 매개변수는 종종 "함수 두 개를 숨긴 신호"야.**

## 4. 신뢰의 경계 — 검증은 서버에서

폼에 `required`, `min={0}` 다 박았어. 그런데 서버액션에서 **또** 검증해:

```ts
if (!name) return { error: "상품명을 입력하세요." };
if (price < 0) return { error: "가격을 0 이상으로..." };
```

중복 아니야. **클라이언트 검증은 UX(빠른 피드백)이고, 서버 검증은 보안(진짜 방어선)이야.**
- HTML `required`는 개발자도구로 1초면 우회해. `curl`로 서버액션 때리면 폼은 거치지도 않아.
- **"클라이언트에서 막았으니 됐다"는 신입의 가장 흔한 보안 구멍이야.** 입력은 항상 서버에서 다시 의심해라. 클라이언트는 적이 통제할 수 있는 영역이다.

`status`도 화이트리스트(`STATUSES.includes`)로 막았어 — DB의 CHECK 제약과 같은 규칙을 코드에도 둬서, 잘못된 값이 DB까지 가서 거부당하기 전에 잡는다.

## 5. 검증할 땐 흔적을 남기지 마라 (또)

이 기능은 조회만으로 못 끝내. 등록이 진짜 되는지 보려면 **실제로 만들어봐야** 해. 그래서:
1. `[테스트] 유기농 당근`을 등록 → 목록 상단 노출 확인
2. 수정으로 상태 품절 변경 → 반영 확인
3. **끝나고 그 테스트 상품을 삭제** → DB 원상복구 (`name like '[테스트]%'`로 안전하게)

이름에 `[테스트]` 접두사를 붙인 건 의도적이야 — **삭제할 때 정확히 그것만** 지우려고. 운영 데이터를 건드리지 않게 "내가 만든 것"에 표식을 남기고, 끝나면 그 표식으로 청소해. **검증의 시작과 끝은 "들어왔던 흔적이 없게"야.**

---

## 6. 한눈에 — 오늘 추가된 휴리스틱

1. **선언 ≠ 존재.** SQL 파일에 있다고 라이브에 있는 게 아니다. 인프라는 만들기 전에 핑.
2. **직접 결정 vs 물어보기 = "혼자 되돌릴 수 있나 + 네 행동이 필요한가".**
3. **통합은 공통이 분기보다 클 때.** 불리언 플래그 매개변수는 "함수 둘"의 신호일 때가 많다.
4. **신뢰의 경계는 서버.** 클라이언트 검증은 UX, 서버 검증은 보안. 둘 다 한다.
5. **검증은 흔적 없이.** 테스트 데이터엔 표식을 달고, 끝나면 그 표식으로 청소.
